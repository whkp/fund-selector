# 基金罗盘真实数据与公开服务改造方案（旧版调研记录）

**版本：v1.0**
**日期：2026-08-09**
**目标：将当前本地 Mock MVP 演进为可控公开演示站，再演进为具备真实数据、可追溯研究和安全边界的基金研究服务。**

## 1. 结论与技术路线

GitHub 调研的主要参考项目是：

- `StanleyChanH/FUND-SELECTOR-CN`：Python + Streamlit + Tushare Pro；使用基金净值、基金基本信息和指数数据，在本地计算收益、波动率、回撤和夏普等指标。
- `nisxu/akshare-fund-skill`：Python + AKShare；以全市场基金列表、基金排行、单基金历史净值和 ETF 行情为输入，并采用 TTL 缓存。
- `samwancd/akshare_fund_analyzer`：Python + AKShare；批量拉取基金历史净值，计算风险指标和评分，输出 CSV 和图表。

上述有实际数据代码的项目均以 Python 为主。它们适合研究脚本、个人分析工具和数据探索，但不构成当前项目必须迁移到 Python 的理由。当前项目应当保留 **Vue 3 + TypeScript 前端、Go 在线 API 与 Go Worker**，把开源项目中有效的“数据适配、缓存、历史序列计算、批量刷新”模式吸收进来。

推荐的目标形态：

```text
Vue 3 Web
    |
    v
Go API（认证、查询、筛选、研究运行、AI Guardrail）
    |
    +--> PostgreSQL（事实、快照、用户数据、审计记录）
    +--> Redis（缓存、限流、短任务状态）
    +--> Worker（采集、解析、校验、指标、索引任务）
    |        |
    |        +--> 数据适配器（授权源优先；公开源仅开发/参考）
    |
    +--> LLM Gateway（固定服务端配置、结构化意图理解）
```

Python 的合理位置是可选的离线研究工具，例如指标口径验证、历史回测、数据质量抽样和临时数据分析；它不应成为公开站点实时请求依赖，也不应被浏览器直接调用。

## 2. 当前状态与改造原则

当前 MVP 已有 Vue 前端、Go API、规则式筛选、推荐 Trace、腾讯公开 ETF 行情参考、东方财富/天天基金公开日频净值参考和可选云端 LLM 调用。其限制是基金全集仅有 5 条嵌入式数据，收益/波动/回撤/评分/曲线大多是 Mock，所有状态保存在 API 进程内存。

改造必须遵守以下原则：

1. **先替换数据层，再丰富 AI。** LLM 只能理解目标、组织问题和解释已验证事实，不能生成基金事实或指标。
2. **事实与派生结果分离。** 原始响应、标准化事实、指标快照和推荐结果都必须独立保存、可追溯。
3. **正式净值和盘中行情分离。** 普通开放式基金的正式 NAV 是日频披露；ETF/LOF 场内价格、IOPV 和估算值不得混写为同一字段。
4. **公开接口只作为开发参考。** AKShare、东方财富、腾讯财经等可用于开发验证和人工比对，不能默认视为可公开再分发的生产数据源。
5. **数据缺失宁可降级，不可伪造完整。** 历史不足、来源低信任、指标未重算时，明确显示 `INSUFFICIENT`、`STALE` 或 `REFERENCE`。
6. **在线请求不直接批量抓取网页。** 页面读数据库/缓存；抓取和计算由受控 Worker 异步完成。

## 3. 技术栈决策

| 层级 | 推荐技术 | 当前状态 | 改造理由 |
|---|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite | 已有 | 继续沿用；后续加入 Vue Router、Pinia、组件测试。 |
| 在线 API | Go 标准库或 `chi` | Go 标准库 | 保留 Go；适合并发 API、采集编排、SSE、可执行二进制部署。引入路由库不是当前必需。 |
| 数据访问 | `pgx` + SQL 迁移工具 | 无 | 推荐 PostgreSQL 作为主事实库；`pgx` 性能和 PostgreSQL 类型支持较好。 |
| 数据库 | PostgreSQL 16+ | 内存仓库 | 支持 JSONB、时间序列索引、事务、审计与备份。MySQL 8 也可行，但 PostgreSQL 更适合快照与查询条件组合。 |
| 缓存与限流 | Redis 7+ | 无 | 用于热门查询缓存、分布式锁、限流、短生命周期任务状态；不能作为唯一事实来源。 |
| 后台任务 | Go Worker + PostgreSQL Outbox | API 内 goroutine | 先不用 RabbitMQ；规模较小时使用任务表/Outbox 足够，之后再按吞吐量引入消息队列。 |
| 搜索 | PostgreSQL FTS + `pg_trgm` 起步 | 无 | 基金代码/名称/经理/公司检索先在 PostgreSQL 完成；只有语义检索和规模需求成熟后再增加 OpenSearch。 |
| 向量检索 | `pgvector`，按需启用 | 无 | 若自然语言主题匹配不足，再启用；不应成为真实筛选的前置依赖。 |
| 指标计算 | Go 生产实现；Python 校验脚本可选 | 固定 Mock 值 | 生产计算靠 Go Worker 保持单一在线技术栈；Python 可用于验证 Go 结果与研究探索。 |
| LLM | OpenAI-compatible HTTPS provider | 已有 | 保持服务端固定配置、结构化输出、失败回退；禁止公网用户修改全局 provider。 |
| 反向代理 | Caddy 或 Nginx | 无 | 同源转发 `/api`、TLS、压缩、安全头、静态文件缓存。 |
| 监控 | Prometheus + Grafana + 结构化日志 | `slog` 基础日志 | 监控 API、数据源、Worker、指标任务和 LLM 成本。 |
| CI/CD | GitHub Actions | 无 | 运行单测、静态检查、前端构建、镜像或二进制发布、数据库迁移检查。 |

### 3.1 为什么不将在线系统整体迁移到 Python

Python 项目的数据生态确实丰富，尤其是 AKShare、Pandas 和量化分析库。但迁移会导致当前已完成的 Go API、AI 适配、SSE 和数据模型推倒重来，同时引入两套在线服务的部署与安全边界。推荐保留 Go 的原因：

- 当前服务端实现已是 Go，迁移收益小于迁移成本。
- Go 适合并发采集、限流、超时、长连接和单二进制部署。
- 收益率、波动率、回撤、夏普等核心计算公式简单、稳定，可在 Go 中实现并覆盖单元测试。
- 对外产品关键在于数据授权、快照、质量和审计，而不是使用何种语言。

可以建立 `tools/research-python/`，仅放入可复现的 Python Notebook/脚本，用于：从同一份 CSV/Parquet 验证指标、对照 Pandas 结果、回测实验和数据巡检。其输出必须经正式数据管道验证后才能进入数据库。

## 4. 数据源与许可分层

### 4.1 生产数据优先级

| 数据类别 | 生产首选 | 开发/参考备选 | 当前状态 | 使用边界 |
|---|---|---|---|---|
| 基金主数据 | 已签约基金数据商或官方披露适配器 | Tushare Pro、AKShare/东方财富 | Mock | 代码、名称、类型、成立日、公司、经理、费率、状态必须有来源和业务日期。 |
| 正式单位/累计净值 | 授权数据商，管理人/托管人/电子披露校验 | 东方财富/天天基金公开历史净值 | 仅少量公开参考 | 用于收益和风险指标；不以盘中估值替代。 |
| 历史净值序列 | 授权历史净值库 | AKShare/Tushare/公开历史接口 | 未完成 | 原始序列不可覆盖；必须保留复权/累计净值口径。 |
| ETF/LOF 场内行情 | 交易所或授权行情供应商 | 腾讯财经、AKShare | 少量公开参考 | 仅行情展示；不替代正式 NAV。 |
| ETF IOPV/申赎清单 | 交易所、基金公司或授权供应商 | 无 | 未接入 | 仅作为参考值；必须独立字段存储。 |
| 持仓、规模、费率、经理 | 季报/公告/授权数据商 | AKShare/Tushare | Mock | 事件或定期披露驱动，不能假定为实时。 |
| 公告、申赎与状态 | 基金电子披露网站、基金公司、交易所 | 公开聚合源 | 未接入 | 影响可申购性和风险提示，应有发布日期与文档版本。 |
| 基准指数 | 指数公司/授权行情 | Tushare/AKShare | 未接入 | 用于相对收益、Beta、跟踪误差，需定义基准映射。 |

### 4.2 接入前的许可检查

对任何源，在技术接入前记录并经人工确认：

```text
是否允许自动访问
是否允许批量拉取与本地缓存
是否允许向最终用户展示
是否允许商业使用
是否需要来源署名
限流、SLA、字段口径与数据延迟
是否允许生成衍生指标与推荐研究结果
```

公开数据源的适配器必须标识 `sourceType=AGGREGATED_PUBLIC`、`trustLevel=LOW/MEDIUM` 和许可边界；只有被允许的来源才能进入公开站点的核心事实链路。

### 4.3 适配器接口

在 Go 中定义稳定的领域接口，而不是让业务逻辑依赖 AKShare、Tushare 或某个网页字段：

```go
type FundUniverseProvider interface {
    ListFunds(ctx context.Context, cursor string) (FundPage, error)
}

type FundProfileProvider interface {
    GetProfile(ctx context.Context, code string) (FundProfileRecord, error)
}

type NAVHistoryProvider interface {
    ListNAV(ctx context.Context, code string, from, to time.Time) ([]NAVRecord, error)
}

type QuoteProvider interface {
    ListQuotes(ctx context.Context, codes []string) ([]QuoteRecord, error)
}

type DisclosureProvider interface {
    ListEvents(ctx context.Context, since time.Time) ([]DisclosureEvent, error)
}
```

每个返回记录都必须携带：`sourceName`、`sourceType`、`sourceRecordKey`、`sourceURL`、`businessDate`、`fetchedAt`、`trustLevel`、`licenseScope` 和 `parserVersion`。

## 5. 目标数据架构

### 5.1 数据流水线

```text
Data provider
    -> acquisition run
    -> raw_data_snapshots（原始响应、hash、抓取元数据）
    -> parser/normalizer
    -> data_snapshots（标准化事实、质量状态）
    -> fund_* tables（主数据、NAV、行情、公告）
    -> metric calculation jobs
    -> fund_metric_snapshots（带计算版本）
    -> search/cache refresh
    -> recommendation run（绑定 immutable snapshot）
```

线上页面只能读取已通过质量门槛的标准化快照和派生指标；不可在用户请求中临时抓取外站来填充研究结论。

### 5.2 最小数据库表

第一期不需要立即引入全部设计稿表，但以下表是从 Mock 过渡到真实数据的最小集合：

| 表 | 关键字段 | 用途 |
|---|---|---|
| `funds` | `id, code, name, type, inception_date, latest_snapshot_id` | 稳定基金身份和当前主数据指针。 |
| `data_source_configs` | `source_name, source_type, license_scope, enabled` | 来源配置与许可边界。密钥仅引用 secret，不存明文。 |
| `acquisition_runs` | `source_id, started_at, finished_at, status, error_summary` | 采集作业审计与监控。 |
| `raw_data_snapshots` | `source_id, fetched_at, content_hash, object_key, parser_version` | 可重放的原始证据；大响应放对象存储，表只存元数据。 |
| `data_snapshots` | `raw_snapshot_id, business_date, quality_status, normalized_hash` | 标准化快照门禁。 |
| `fund_nav_snapshots` | `fund_id, snapshot_id, nav_date, unit_nav, accumulated_nav, nav_type` | 正式/估算 NAV 分开保存。 |
| `fund_quote_snapshots` | `fund_id, snapshot_id, quote_time, market_price, amount, venue` | ETF/LOF 场内行情。 |
| `fund_metric_snapshots` | `fund_id, snapshot_id, window_code, metric_version, return_1y, volatility, drawdown, sharpe` | 可复算指标。 |
| `fund_events` | `fund_id, snapshot_id, event_type, published_at, title, source_url` | 经理、申赎、公告等事件。 |
| `users`、`risk_profiles`、`watchlist_items` | `user_id` 外键 | 用户隔离。 |
| `recommendation_runs`、`recommendation_candidates`、`recommendation_steps` | `user_id, data_snapshot_id, policy_version, model_version` | 可审计研究过程。 |
| `outbox_events`、`job_runs` | `event_type, payload, status, attempts` | 可靠异步执行与补偿。 |

核心约束：快照和指标只追加、不原地覆盖。`latest_*` 可以是索引或视图，但历史推荐始终指向其创建时的快照。

### 5.3 数据质量规则

每个字段级别独立输出：

```text
PASS        可作为当前研究事实
REFERENCE   可展示为参考，不能进入核心评分
STALE       超过字段新鲜度阈值
MISSING     缺少数据
CONFLICT    多源不一致，等待人工或规则处理
SUSPICIOUS  异常涨跌、日期倒退、零值等校验失败
```

最低校验规则：

- 基金代码格式、名称和类型必须与主数据一致。
- NAV 日期不能晚于抓取日，单位净值必须大于零。
- 相邻净值异常变化必须进入 `SUSPICIOUS` 队列，不自动覆盖上一条有效快照。
- 累计净值不应在无分红/拆分事件下异常回退。
- 历史序列必须单调日期、去重、标记缺失交易日。
- 指标窗口不足时输出 `INSUFFICIENT_HISTORY`，不输出伪精确数字。
- ETF 市场价格、IOPV、正式 NAV、估算 NAV 必须是不同字段和不同来源类型。

## 6. 同步、缓存与 Worker 设计

### 6.1 任务类型和刷新策略

| 任务 | 频率/触发 | 结果 | 失败策略 |
|---|---|---|---|
| 基金全集与基础资料 | 每日/每周全量，公告增量 | 主数据快照 | 保留上一版，标记来源延迟。 |
| 正式 NAV 增量 | 交易日 16:00-23:30 周期轮询，次日补偿 | NAV 历史 | 不将估算值替代正式值。 |
| 历史 NAV 回补 | 新基金、数据缺口、数据源修复时 | 补齐序列 | 分批、限流、可恢复。 |
| ETF/LOF 行情 | 交易时段 3-15 秒或供应商推送 | 最新报价 + 必要历史 | 过期后标记 `STALE_QUOTE`。 |
| 公告/申赎状态 | 5-30 分钟，夜间补偿 | 事件快照 | 与主数据状态对账。 |
| 指标重算 | NAV/事件变更触发 | 指标快照 | 幂等键：基金、快照、窗口、算法版本。 |
| 搜索索引/缓存失效 | 事实或指标更新事件 | 读模型 | 允许最终一致，不影响事实审计。 |

### 6.2 分阶段的任务基础设施

第一期使用 PostgreSQL 任务表和 Outbox，不需要 RabbitMQ：

```text
业务事务提交 fund_nav_snapshot
    -> 同事务写入 outbox_events(metric.recalculate)
    -> worker 领取未完成事件（FOR UPDATE SKIP LOCKED）
    -> 计算并写入 metric snapshot
    -> 标记事件已完成
```

这能解决 API 内 goroutine 重启丢任务、重复消费和无补偿的问题。并发和吞吐量确实成为瓶颈后，再将 Outbox 投递到消息队列。

Redis 的职责仅包括：

- 热门基金详情、热门排行和公共筛选结果缓存；
- per-IP/per-user 限流；
- 单飞锁/短期去重；
- SSE 或异步研究任务的短时状态。

Redis 宕机不能丢失基金事实或推荐审计记录。

## 7. 指标、评分与推荐改造

### 7.1 指标计算口径

第一期只使用正式日频净值，按交易日/有效净值序列明确计算：

| 指标 | 公式或规则 | 最低样本要求 |
|---|---|---|
| 区间收益 | `last_nav / first_nav - 1` | 窗口内至少 2 个有效点。 |
| 年化收益 | `(last / first)^(annual_days / elapsed_days) - 1` | 至少 90 天；样本不足单独标识。 |
| 年化波动率 | 日收益率标准差 `* sqrt(252)` | 至少 60 个有效净值点。 |
| 最大回撤 | `nav / rolling_max(nav) - 1` 的最小值 | 至少 2 个有效点。 |
| 夏普比率 | 年化超额收益 / 年化波动 | 风险自由利率和版本必须记录。 |
| 卡玛比率 | 年化收益 / abs(最大回撤) | 最大回撤非零。 |
| 同类分位 | 同类别、同窗口、同快照的横向百分位 | 同类样本达到最低数量。 |

指标表中必须记录：`metricVersion`、`windowCode`、`inputSnapshotIds`、`businessDate`、`calculatedAt`、`riskFreeRateVersion` 和 `insufficiencyReason`。

### 7.2 推荐的确定性层

LLM 不参与基金事实与硬约束决策。推荐顺序应是：

```text
用户确认的风险画像
    -> 硬过滤（基金状态、风险、可申购性、费用、数据质量、样本长度）
    -> 同类/主题候选召回
    -> 基于真实指标的版本化评分
    -> 组合集中度与观察列表重合检查
    -> LLM 仅解释、追问与整理对比结论
    -> 引用、免责声明与数据日期校验
```

建议的 `research-score-v1` 组成，权重需通过回测和人工评审确定：

| 维度 | 初始权重 | 输入 |
|---|---:|---|
| 用户约束与目标匹配 | 30% | 主题、期限、费率、流动性、风险画像。 |
| 风险适配 | 25% | 风险等级、波动、最大回撤、样本充分性。 |
| 长期风险调整表现 | 25% | 年化收益、夏普、卡玛、同类分位。 |
| 费用与可得性 | 10% | 管理/托管/申赎费和申购状态。 |
| 数据质量 | 10% | 来源信任、新鲜度、冲突、缺失。 |

不能把短期收益当作主要推荐依据；不同行业、资产类别和成立年限的基金应在可比集合内比较。每个候选都要输出贡献分、被排除原因和数据缺口。

### 7.3 AI 的最终职责与限制

保留现有 OpenAI-compatible 适配层，但收敛 AI 能力：

- 允许：意图抽取、结构化筛选条件补全、比较摘要、风险提示归纳、追问生成。
- 不允许：编造基金、收益、公告、数据日期或来源；绕过风险/质量硬过滤；输出买卖指令和收益承诺。
- 工具输入输出采用 JSON Schema；模型返回通过 schema 校验和业务校验。
- 每个 Run 持久化 provider、model、prompt version、tool schema version、输入快照和降级状态。
- 公网固定为服务端环境变量/Secret Manager 配置。`/api/ai/configure` 和 `/api/ai/reset` 只能在本地开发或管理员受控环境启用。

## 8. API、前端与安全改造

### 8.1 API 边界

将现有 API 拆为公共只读、认证用户和管理员三类：

| 范围 | 示例接口 | 访问策略 |
|---|---|---|
| 公共只读 | `GET /api/funds`、`GET /api/funds/{code}`、`GET /api/market/etf-quotes` | 限流、缓存、仅展示已许可和可公开的数据。 |
| 认证用户 | `POST /api/recommendations/runs`、`/api/profile/*`、`/api/watchlist/*` | session/JWT，所有数据按 `user_id` 隔离。 |
| 管理接口 | 数据源状态、手动刷新、AI 配置、任务重放 | 管理员认证、审计日志、最好与公网 API 隔离。 |

生产 API 要补齐：请求超时、body 限制、panic recovery、精确 CORS allowlist、CSRF/session 防护、限流、统一错误码、日志脱敏、健康/就绪探针和优雅关闭。

### 8.2 前端改造

1. 去除 API 失败后的静默 Mock 研究结果；开发环境可降级，公开环境显示明确不可用状态。
2. 引入 `dataMode`：`DEMO`、`REFERENCE`、`LIVE_LICENSED`；页面顶部固定展示模式、数据截至时间、来源与免责声明。
3. 在基金详情将 `officialNav`、`estimatedNav`、`marketPrice`、`iopv` 分栏展示，不能使用单一 `nav` 模糊表达。
4. 基金详情与对比页面显示指标窗口、计算版本、样本数量、数据新鲜度和不足原因。
5. 只有用户登录后显示观察列表、风险画像、历史研究；公开 Demo 使用只读固定示例。
6. 将当前 AI Key 弹窗改为仅 `LOCAL_DEVELOPMENT` 可见；公开站只展示“研究引擎状态”和隐私说明。
7. 使用 Vue Router 区分筛选、基金详情、对比、观察和设置页面；使用 Pinia 管理服务端状态、加载/异常状态和用户会话。

### 8.3 公开部署

```text
Browser
  -> HTTPS / CDN / Caddy or Nginx
  -> static Vue assets
  -> same-origin /api reverse proxy
  -> Go API
  -> PostgreSQL / Redis / Worker / Secret Manager
```

禁止直接公开 Vite dev server。域名、TLS、反向代理、CORS、安全响应头、压缩、缓存和进程管理必须在部署层配置。开发和生产使用不同配置文件，生产密钥只注入 API/Worker 进程，不进入前端构建产物。

## 9. 分阶段实施计划

### Phase 0：公开 Demo 安全化（1-2 周）

目标：在数据仍不完整时，可对外展示产品交互而不误导用户。

- 新增 `FUND_COMPASS_MODE=demo|reference|production`。
- DEMO 页面全局显示“示例数据/非投资建议/仅 5 条候选”。
- 禁止公网 AI 配置、AI reset、数据手动刷新和共享写入接口。
- API 不可用时显示错误页或受控 Demo 标签，不再伪装为最新研究结果。
- 采用 Caddy/Nginx + HTTPS + same-origin API；补齐 server 超时、recover、限流和基础安全头。
- 将所有 `授权数据源`、`官方披露已校验`、`HIGH trust` 等不符合实际的 Mock 文案改为真实状态。

**验收：** 公网访客无法更改全局模型、无法写入其他人的状态；页面不会将 Mock 标为实时真实数据。

### Phase 1：真实数据闭环（2-4 周）

目标：用真实、可复现的少量基金数据替换最核心 Mock 字段。

- 引入 PostgreSQL、迁移、Repository 接口和本地开发 seed。
- 建立 `funds`、`raw_data_snapshots`、`data_snapshots`、`fund_nav_snapshots`、`fund_metric_snapshots`、`job_runs`。
- 实现一个开发参考适配器：优先选择 Tushare Pro 或 AKShare 的稳定封装，严格标记许可和信任等级。
- 同步一小批人工确认的基金集合，而不是立即全市场抓取。
- 保存完整历史日频 NAV；补齐正式 NAV 与累计 NAV 口径。
- 在 Go Worker 实现近 1/3/6/12 月收益、年化波动、最大回撤和夏普，增加公式单测和固定样本回归测试。
- 用 Python 对照脚本验证 Go 指标，误差阈值写入测试。
- 让 `/api/funds`、详情、对比和推荐读取数据库指标快照。

**验收：** 至少 20-50 只已确认基金使用真实历史净值；每个指标可追溯到输入 NAV 快照和计算版本；重启不丢失数据。

### Phase 2：全市场筛选与数据质量（4-8 周）

目标：从固定候选走向受控的全市场研究筛选。

- 接入受许可的基金目录、主数据、基金排行与公告源；确认再分发范围。
- 支持基于类型、费率、规模、成立日、申赎状态、收益和风险指标的数据库筛选。
- 实现基金历史数据回补、断点续传、交易日历和数据异常队列。
- 增加字段级质量报告、多源冲突校验和原始响应 hash。
- 增加公告、经理变更、申赎状态和费率变化事件。
- 使用 PostgreSQL FTS + `pg_trgm` 支持代码、名称、经理和主题检索；评估后再决定是否引入向量检索。
- 将评分从 Mock 分数替换为 `research-score-v1`，保存因子贡献与排除原因。

**验收：** 筛选结果不再受 5 只基金限制；过期或缺失关键数据不会进入核心推荐；数据源故障可观测、可补偿。

### Phase 3：用户与可追溯研究（3-5 周）

目标：支持小范围真实用户试用。

- 引入登录、会话、用户隔离和账户删除流程。
- 持久化风险画像、观察列表、备注、研究运行、候选、Trace 与事件。
- 对每次推荐固定 `data_snapshot_id`、`policy_version`、`metric_version`、`model_version`。
- 引入观察列表变更提示：净值过期、公告、经理变更、申赎状态变化和指标恶化。
- 将 AI 输出限制为结构化意图与解释，添加调用额度、速率限制、成本监控和隐私提示。
- 建立推荐评测集：筛选正确率、硬约束违反率、引用完整率、数据新鲜度和降级率。

**验收：** 任一研究结果可重放和解释；用户之间无法读取/修改彼此的 profile、watchlist 或 runs。

### Phase 4：生产化与公开服务（持续迭代）

目标：满足可运营、可审计的公开服务基础。

- 授权数据源合同、来源归因与法律审核完成。
- 引入 Redis、Outbox Worker、多实例任务锁、重试退避和灾难恢复。
- Prometheus/Grafana、错误追踪、数据源质量告警、LLM 调用/成本告警。
- GitHub Actions：Go 测试、前端 typecheck/build、迁移检查、依赖安全扫描、部署流程。
- 数据库备份、恢复演练、迁移回滚方案、压测、故障注入与安全审计。
- 仅在政策、牌照与合规审查允许的范围内扩展个性化功能；始终保留研究辅助和非交易边界。

## 10. 优先级与下一步

推荐的下一次开发迭代不是再新增 AI 文案，而是实施 Phase 0 与 Phase 1 的第一批工作：

1. 增加运行模式，先把 Demo/真实参考数据状态清楚展示出来，并关闭公网全局 AI 配置。
2. 引入 PostgreSQL 和 migration，先将基金、NAV 快照、指标快照和任务运行落库。
3. 选择并确认一个开发参考数据源，针对 20-50 只基金完成完整历史 NAV 同步。
4. 在 Go 中实现指标计算和回归测试，使用 Python/Pandas 仅做离线对账。
5. 用真实指标替换 `mock_metric_v1`、固定曲线、固定收益/波动/回撤和固定推荐基础分。

在完成这五项前，系统应继续定位为本地研究 MVP 或明确标识的公开 Demo，不应作为真实基金推荐服务对外承诺。
