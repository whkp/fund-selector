# 基金罗盘生产化改造执行计划

**版本：v1.0**  
**制定日期：2026-09-08**  
**适用仓库：`fund-selector`**  
**目标：将当前“本地研究 MVP + AKShare 公开参考数据”逐步改造成可供小范围真实用户使用、可审计、可运维的基金研究服务。**

---

## 1. 执行结论

当前项目可以继续作为本地研究工具和明确标注的 Reference Demo，但不应直接作为多用户公开服务。改造必须按以下顺序推进：

```text
先收敛公开边界
  -> 再建立数据库和数据快照
  -> 再建立同步/指标 Worker
  -> 再补齐认证和用户隔离
  -> 再修正筛选、评分和研究证据链
  -> 最后做生产部署、监控、合规和灰度发布
```

不要先扩展更多 AI 文案或页面模块。当前最大的风险不是 UI 不够丰富，而是数据、状态、权限和研究结果无法稳定复现。

### 1.1 四个发布级别

| 级别 | 允许的能力 | 数据要求 | 用户与运维要求 | 本计划对应阶段 |
|---|---|---|---|---|
| 本地 MVP | 单人研究、手动刷新、会话级模型 | AKShare 公开参考数据 | 可接受进程内状态 | 当前 |
| Reference Demo | 公开只读浏览、有限研究演示 | 公开参考数据，明确低信任和截至时间 | 匿名只读、无共享写入、基础监控 | Phase 0-2 |
| 小范围 Beta | 邀请用户保存观察、风险画像和研究记录 | 可复现快照，至少 20-50 只基金有历史指标 | 登录、用户隔离、数据库、备份、限流 | Phase 3-4 |
| Production | 对外稳定提供研究服务 | 已确认授权或官方数据源 | 完整安全、合规、监控、灾备和回滚 | Phase 5 |

### 1.2 总体完成定义

只有同时满足以下条件，才能把运行模式标记为 `PRODUCTION`：

- 数据源已完成授权、自动访问、缓存、再分发和来源署名确认。
- 基金事实、NAV、行情、指标、研究 Run 均有数据库快照和版本引用。
- 所有用户写数据按 `user_id` 隔离，重启或多实例部署不丢失。
- 缺失或过期的关键字段不能进入核心研究候选。
- API 有认证、权限、限流、请求大小限制、精确 CORS 和统一错误码。
- Worker 有重试、幂等、失败队列和数据质量告警。
- 前后端、数据库迁移、Worker、依赖扫描和关键流程测试在 CI 中通过。
- 完成隐私政策、数据来源说明、投资研究边界和安全审核。

## 2. 当前基线与主要问题

### 2.1 当前已具备

- Vue 3 + TypeScript 前端和 FastAPI/Python 后端可以本地启动。
- 已接入 AKShare 基金目录、开放式基金排行、单基金历史 NAV 和 ETF 行情参考。
- LLM 已支持 OpenAI-compatible/Ollama 结构化 JSON 输出，并校验基金代码是否属于候选池。
- 已有指标计算基础、数据来源状态、知识库协议和研究 Trace 展示。
- 当前验证：后端测试、前端 typecheck 和生产构建均可通过。

### 2.2 必须优先解决

| 问题 | 现状 | 影响 | 目标 |
|---|---|---|---|
| 运行模式 | `PRODUCTION` 仍使用 AKShare Reference 数据 | 可能误把低信任数据当生产数据 | 生产模式必须绑定授权 Provider |
| 存储 | 基金、历史、观察列表、研究 Run 全在进程内存 | 重启丢失，多实例不一致，无法审计 | PostgreSQL + 不可变快照 |
| 数据更新 | 请求时直接调用外部接口，Worker 只执行一次 | 慢、易超时、无补偿、无稳定截至时间 | 独立同步和指标任务 |
| 权限 | 观察列表、研究 Run、刷新接口无认证 | 用户数据串写，刷新接口可被滥用 | Auth + RBAC + user_id 隔离 |
| 筛选 | 未获取的风险/费用/申购状态可能被当作通过 | 研究硬约束不可信 | 缺失关键字段默认不通过 |
| 指标 | 只按需计算，字段未持久化，样本门槛不足 | 结果不能重放，指标口径不稳定 | 版本化指标快照和质量门禁 |
| 前端闭环 | 风险页/复盘页是占位，备注未保存，筛选项部分未传后端 | 用户流程不完整 | 页面状态与服务端契约一致 |
| 运维 | 无就绪探针、告警、备份、恢复演练和完整 CI | 无法判断服务是否可用 | 生产级可观测和发布流程 |

## 3. 目标架构

```text
Browser / GitHub Pages 或同源静态站
        |
        v
HTTPS Reverse Proxy / CDN
        |
        +--> FastAPI API
        |      +--> Auth / RBAC / Rate Limit / Request Limit
        |      +--> Screening / Metrics / Research / User Services
        |      +--> PostgreSQL Repository
        |      +--> Redis（按需：限流、热点缓存、短任务状态）
        |
        +--> Worker
               +--> Fund Universe Sync
               +--> NAV History Sync
               +--> Data Quality Gate
               +--> Metrics Recalculation
               +--> Outbox / Retry / Dead Letter

Data Providers
  -> Licensed Provider（Production）
  -> AKShare（Reference/开发，必须标注 LOW）

LLM Gateway
  -> server-side Secret
  -> allowlisted host
  -> quota / timeout / redacted audit
  -> structured output only
```

### 3.1 代码边界

后续改造应逐步从当前单文件路由迁移到以下边界，不要求一次性重写：

```text
backend/app/
├── api/              # HTTP 路由、认证依赖、请求/响应 Schema
├── core/             # 配置、安全、日志、错误、限流
├── db/               # SQLAlchemy、会话、迁移、Repository
├── domain/           # Fund、Snapshot、Metric、Research 领域模型
├── providers/        # AKShare、授权源、Provider 协议
├── services/         # 筛选、指标、研究、用户和数据质量服务
├── agent/            # 只读工具、结构化输出、证据绑定
└── workers/          # 同步、计算、重试、调度
```

迁移期间保留现有 API 路径，先替换内部实现，再考虑 API v2。禁止让前端直接依赖 Provider 的 DataFrame 或供应商字段。

## 4. 阶段总览与建议节奏

以下周期按一名熟悉项目的工程师全职推进估算；如果同时处理数据供应商、合规或视觉重构，周期应相应增加。

| 阶段 | 目标 | 预计周期 | 发布结果 |
|---|---|---:|---|
| Phase 0 | 公开边界和基础安全收敛 | 3-5 个工作日 | 可安全部署 Reference Demo |
| Phase 1 | PostgreSQL、迁移和快照仓库 | 1-2 周 | 重启不丢核心数据 |
| Phase 2 | 数据同步、质量门禁和指标 Worker | 2-3 周 | 20-50 只基金有可复现指标 |
| Phase 3 | 筛选、评分、对比和研究证据链 | 1-2 周 | 研究结果可解释、可重放 |
| Phase 4 | 登录、用户数据和前端功能闭环 | 2-3 周 | 邀请用户 Beta |
| Phase 5 | 生产运维、合规和灰度发布 | 2-4 周 | 满足 Production 发布门槛 |

阶段可以并行准备，但发布门槛不能跳过。Phase 0 未完成前不要公开写接口；Phase 1-2 未完成前不要承诺“实时”和“稳定推荐”；Phase 4 未完成前不要保存真实用户数据。

## 5. Phase 0：Reference Demo 安全收敛

**目标：** 允许公开展示页面和只读基金数据，但不让匿名访客修改共享状态、触发高成本任务或误解数据可信度。

### 5.1 后端任务

1. 增加明确的运行模式：`LOCAL`、`REFERENCE`、`PRODUCTION`。
2. `REFERENCE` 模式只开放：
   - `GET /health`
   - `GET /api/funds`
   - `GET /api/funds/{code}`
   - `GET /api/funds/{code}/history`
   - `GET /api/funds/{code}/data-quality`
   - `GET /api/market/etf-quotes`
   - `GET /api/data-sources/status`
3. 暂时关闭或改成管理员接口：
   - `POST /api/data/funds/refresh`
   - `POST /api/market/etf-quotes/refresh`
   - 所有观察列表写接口
   - 所有风险画像写接口
   - 服务端 AI 配置和重置接口
4. 将 CORS 从 `*` 改为明确的允许来源列表；生产优先使用同源反向代理。
5. 增加统一异常处理：验证错误、业务错误、上游错误、内部错误统一返回：

```json
{
  "error": {
    "code": "DATA_SOURCE_UNAVAILABLE",
    "message": "当前数据源暂不可用",
    "requestId": "req_xxx",
    "retryable": true
  }
}
```

6. 增加请求体大小、查询字符串长度和并发上限；所有外部请求设置连接、读取和总超时。
7. `/health` 保持进程存活检查；新增 `/ready`，至少检查数据库连接、最近一次数据快照和关键配置。
8. 生产日志必须脱敏：禁止记录 API Key、Authorization、研究请求中的完整 Key 和模型原始敏感内容。

### 5.2 LLM 任务

- 公网关闭 BYOK 设置入口；本地开发通过配置开启。
- 服务端 LLM 地址也执行 host allowlist、HTTPS、超时、最大响应体和调用额度校验。
- 为每个请求生成 `requestId`，只记录 provider、model、耗时、token 用量和错误类别。
- 未配置或不可用时返回明确状态，不回退成伪造的规则推荐。

### 5.3 前端任务

- 顶部固定显示 `REFERENCE / AKSHARE_PUBLIC / LOW`、最近成功日期和免责声明。
- API 不可用时显示不可用状态，不显示“正在研究”的假结果。
- 关闭匿名观察、备注、风险画像和刷新入口，或明确标为本地功能。
- 明确区分正式 NAV、累计 NAV、场内价格和估算值。

### 5.4 验收

- 未登录访客无法调用任何共享写接口。
- 访客无法通过刷新接口让服务持续抓取上游。
- 页面不会把 AKShare 标为授权、官方或高信任数据。
- 上游超时后 API 在可控时间内返回统一错误，服务进程仍健康。
- 前端 `npm run typecheck`、`npm run build` 和后端测试全部通过。

## 6. Phase 1：数据库、迁移和快照仓库

**目标：** 替换进程内 Repository，建立可恢复、可追溯的事实和派生数据存储。

### 6.1 技术任务

1. 引入 SQLAlchemy Async、asyncpg、Alembic。
2. 增加本地 PostgreSQL 开发配置和测试数据库配置。
3. 所有表使用 UTC 时间；业务日期单独使用 `date`，不能用抓取时间替代。
4. 每次同步使用事务；先写原始快照和标准化快照，再更新当前指针。
5. 使用唯一键和幂等键，避免同一 Provider、基金、业务日期重复写入。
6. 只允许服务层访问数据库；路由不直接拼 SQL。

### 6.2 最小表结构

#### `funds`

- `id`：内部 UUID。
- `code`：基金代码，唯一。
- `fund_type`、`name`、`short_name`。
- `current_profile_snapshot_id`。
- `created_at`、`updated_at`。

#### `fund_profile_snapshots`

- `fund_id`、`provider`、`provider_record_id`。
- `company`、`manager`、`manager_years`、`risk_level`。
- `fee_rate`、`scale`、`inception_date`、`subscription_status`、`theme`。
- `business_date`、`fetched_at`、`source_type`、`trust_level`。
- `quality_status`、`parser_version`、`raw_snapshot_id`。

#### `raw_data_snapshots`

- `source_name`、`endpoint`、`fetched_at`、`business_date`。
- `content_hash`、`payload_uri` 或压缩文本字段。
- `parser_version`、`http_status`、`error_code`。
- 原始大响应超过数据库阈值时存对象存储，数据库只存引用和 hash。

#### `fund_nav_snapshots`

- `fund_id`、`snapshot_id`、`nav_date`。
- `unit_nav`、`accumulated_nav`、`nav_type`。
- `source_type`、`trust_level`、`quality_status`。
- 唯一键：`fund_id + nav_date + nav_type + source_snapshot_id`。

#### `fund_quote_snapshots`

- `fund_id`、`quote_time`、`market_price`、`previous_close`。
- `change_percent`、`amount`、`turnover`、`iopv`、`venue`。
- 明确区分 `market_price` 与 `official_nav`。

#### `fund_metric_snapshots`

- `fund_id`、`input_snapshot_id`、`window_code`。
- `metric_version`、`calculated_at`、`business_date`。
- `total_return`、`annual_return`、`volatility`、`drawdown`、`sharpe`、`calmar`。
- `sample_count`、`status`、`insufficiency_reason`、`risk_free_rate_version`。
- 唯一键：`fund_id + input_snapshot_id + window_code + metric_version`。

#### 用户与研究表

- `users`、`sessions` 或外部身份映射表。
- `risk_profiles`：按用户和问卷版本保存。
- `watchlist_items`：`user_id + fund_id` 唯一。
- `watchlist_notes`：备注历史和更新时间。
- `recommendation_runs`：查询、用户、数据快照、策略版本、模型版本、状态。
- `recommendation_candidates`：候选、决策、证据引用、风险标记。
- `recommendation_steps`：Trace 事件、耗时、错误和输入输出 hash。
- `job_runs`、`outbox_events`：任务状态、尝试次数、下次重试时间和错误分类。

### 6.3 Repository 迁移顺序

1. 保留当前 `DataRepository` 接口，新增 `SqlRepository`。
2. 用 feature flag 让读取路径先支持双读：SQL 优先，内存只作为本地 fallback。
3. 将刷新、历史查询、观察列表和研究 Run 逐项切到 SQL。
4. 加入迁移测试：空库迁移、重复迁移、回滚到上一版本。
5. 删除线上内存 fallback；本地 Demo 如需 seed，必须独立于生产模式。

### 6.4 验收

- 重启 API 后基金、观察列表和研究 Run 仍可读取。
- 两个 API 实例读取同一份数据，用户 A 无法读取用户 B 的写数据。
- 相同输入快照重复运行不会产生重复 NAV、指标或任务记录。
- 数据库迁移可在空库和已有数据上成功执行。

## 7. Phase 2：数据同步、质量门禁和指标 Worker

**目标：** API 只读数据库/缓存，外部抓取、解析和计算由可重试的 Worker 执行。

### 7.1 Provider 适配器

定义统一协议：

```python
class FundUniverseProvider(Protocol):
    async def list_funds(self) -> list[FundBasicRecord]: ...

class FundHistoryProvider(Protocol):
    async def history(self, code: str, start: date, end: date) -> list[NAVRecord]: ...

class FundQuoteProvider(Protocol):
    async def etf_quotes(self, codes: list[str] | None = None) -> list[QuoteRecord]: ...
```

每个 Provider 必须实现：

- 请求超时、重试次数、指数退避和并发上限。
- 返回列集合、类型、日期范围和正值 NAV 校验。
- 原始响应 hash、解析器版本和来源类型。
- 空数据、字段变化、限流、网络失败和业务无数据的分类。
- 许可范围和再分发状态。

### 7.2 同步任务

#### 基金目录任务

- 周期：每日一次或供应商更新后触发。
- 过程：拉取目录 -> 写 raw snapshot -> 标准化 -> 质量门禁 -> 更新当前 profile 指针。
- 失败：保留上一份通过质量门禁的快照，标记 `DEGRADED` 或 `STALE`，不写空数据覆盖现有数据。

#### NAV 任务

- 首批只回补人工确认的 20-50 只基金。
- 新基金、缺口基金和用户打开详情时进入补偿队列。
- 任务按基金分片，单次限制数量，支持断点续传。
- 普通开放式基金使用正式日频 NAV；不得把估算值或 ETF 市价写入 `official_nav`。

#### ETF 行情任务

- 交易时段按供应商能力刷新。
- 超过新鲜度阈值后返回 `STALE_QUOTE`，不能继续标记 `ACTIVE`。
- `marketPrice`、`iopv`、`officialNav` 分开存储和展示。

### 7.3 质量状态

统一使用：

```text
PENDING       尚未成功获取
ACTIVE        在新鲜度阈值内且通过质量门禁
DEGRADED      上游失败但仍有上一份可用快照
STALE         超过新鲜度阈值
INSUFFICIENT  数据不足，不能计算目标指标
CONFLICT      多来源冲突，尚未裁决
ERROR         本次任务失败且无可用快照
```

关键字段缺失规则：

| 字段 | 影响 |
|---|---|
| 基金代码、名称、类型 | 不能进入展示候选 |
| NAV 日期、单位 NAV | 不能计算指标 |
| 风险等级 | 使用风险上限筛选时不能判定为通过 |
| 费率 | 使用最高费率筛选时不能判定为通过 |
| 申购状态 | 开放申购筛选时不能判定为通过 |
| 指标样本不足 | 可以展示，但不能进入依赖该指标的核心排序 |

### 7.4 指标口径

第一版固定并版本化以下口径：

- 区间收益：`last_nav / first_nav - 1`。
- 年化收益：使用实际日期跨度，不使用简单样本数量替代。
- 年化波动：有效日收益标准差乘以 `sqrt(252)`。
- 最大回撤：逐日滚动高点回撤最小值。
- 夏普：年化超额收益除以年化波动，风险自由利率和版本必须记录。
- 最低样本：1 年窗口至少 60 个有效点；低于门槛返回 `INSUFFICIENT`。

每条指标必须可回查：

```text
metric -> input nav snapshot -> raw snapshot -> provider / parser version
```

### 7.5 Outbox 与重试

第一阶段不引入 RabbitMQ，使用 PostgreSQL `outbox_events`：

```text
写入 NAV 快照
  -> 同事务写 metric.recalculate 事件
  -> Worker FOR UPDATE SKIP LOCKED 领取
  -> 计算并写指标快照
  -> 成功标记 completed
  -> 失败递增 attempts 并设置 next_retry_at
  -> 超过阈值进入 dead-letter 状态
```

### 7.6 验收

- API 请求不再直接触发全量外部抓取。
- 20-50 只基金具备 1 年历史 NAV、指标、样本数和质量状态。
- 上游失败不覆盖最近成功快照，页面能看到 `DEGRADED/STALE`。
- Worker 重启后未完成任务可继续执行；重复执行不产生重复快照。
- Provider 字段变化会使测试失败并产生告警，不静默写错数据。

## 8. Phase 3：筛选、评分、对比和研究证据链

**目标：** 将“可展示结果”升级为“规则明确、证据可追溯、模型只负责解释”的研究流程。

### 8.1 筛选服务

1. 前端和后端共享版本化 `ScreenRequest` Schema。
2. 筛选条件至少包括：基金类型、风险上限、费率上限、申购状态、成立年限、指标窗口、收益/波动/回撤阈值。
3. 关键字段缺失时默认 `NOT_ELIGIBLE`，不能静默通过。
4. 每个被排除候选保存 `exclusionReasons`，例如：

```json
{
  "fundCode": "000001",
  "eligible": false,
  "exclusionReasons": ["RISK_LEVEL_MISSING", "FEE_MISSING"]
}
```

5. 筛选结果绑定 `dataSnapshotId` 和 `policyVersion`。

### 8.2 确定性评分

将当前启发式分数替换为 `research-score-v1`：

- 因子、权重、归一化方式写入配置并版本化。
- 每个分数返回因子贡献、缺失因子和排除原因。
- 分数只作为研究排序，不命名为“推荐度”或“收益预测”。
- 同一数据快照、策略版本和筛选条件必须可复算。

建议第一版因子：

| 因子 | 前提 | 备注 |
|---|---|---|
| 收益 | 指标状态为 `PASS` | 绑定窗口 |
| 波动 | 指标状态为 `PASS` | 越低越优需明确方向 |
| 最大回撤 | 指标状态为 `PASS` | 绝对值处理 |
| 费率 | 费率已核验 | 缺失不计分，必要时直接排除 |
| 数据质量 | 来源和新鲜度通过门禁 | 不是收益因子 |

### 8.3 LLM 研究服务

#### 当前实现基线（2026-09-10）

当前代码已经落地一个受限的单次调用 MVP：服务端先执行硬约束筛选、读取最多 60 只候选和最多 5 个本地 Markdown 知识片段，再向 OpenAI-compatible/Ollama 的 `/chat/completions` 发起一次请求。模型只负责意图、主题、摘要、候选临时排序、适配理由、风险提示和追问；它不能访问 AKShare、修改硬约束或创建基金事实。返回后由服务端执行 Pydantic Schema、候选代码白名单、去重和数量校验，并重新绑定服务端基金事实。

因此当前实现不是多步 Agent，也没有模型间复核、流式输出或失败回退推荐。当前模型返回的 `score` 仅为研究展示分，确定性 `research-score-v1`、证据级数值校验、Prompt/模型版本持久化、调用配额和异步 Run 状态机仍按本计划推进。

服务端执行顺序固定为：

```text
解析用户意图
  -> 确定性硬约束
  -> 读取候选和指标快照
  -> 读取知识片段
  -> LLM 生成结构化解释
  -> 校验候选代码、排名、证据引用和风险提示
  -> 持久化 Run / Candidate / Trace
```

必须新增校验：

- ranking 中的基金代码必须唯一且来自候选池。
- 排名数量不能超过请求上限。
- 每个数值结论必须有指标或事实证据引用。
- 不能引用 `STALE`、`INSUFFICIENT` 数据作为最新事实。
- 输出为空、Schema 错误、证据缺失时，Run 标为失败，不返回“已完成”。
- 用户输入和知识库内容只作为不可信文本，不允许模型改变工具权限或硬约束。

### 8.4 对比台

- 对比接口由服务端读取同一 `windowCode` 和同一数据快照。
- 不在前端直接拿基金对象字段假定指标相同。
- 缺失值显示原因而不是只显示 `--`。
- 对比响应返回指标版本、样本数、截至日期和来源。

### 8.5 验收

- 规则测试覆盖未知字段、边界值、风险排序、费率等于阈值和重复基金。
- 固定研究用例可以重复得到同一确定性候选集合。
- LLM 只能解释已验证事实，模型输出越界或无证据时 Run 失败。
- Trace 能回答：使用了哪份数据、哪版策略、哪版指标和哪一模型。

## 9. Phase 4：认证、用户数据和前端功能闭环

**目标：** 支持邀请用户进行真实 Beta 使用，确保每个人只能访问自己的状态。

### 9.1 认证与权限

最小方案：

- 使用成熟身份服务或短期 JWT + refresh token；不要自行实现密码加密协议。
- Access token 短期有效，Refresh token 可撤销并安全存储。
- 密码或身份服务必须支持登录失败限速和账户删除。
- 角色至少为 `user`、`admin`。
- 管理接口与普通 API 分组，数据刷新、任务重放、AI 配置只允许管理员。

所有用户资源都以服务端身份为准，禁止从请求 body 接收 `user_id` 作为授权依据。

### 9.2 用户功能

- 风险画像：问卷版本化保存，修改后生成新版本；研究 Run 引用当时的画像版本。
- 观察列表：用户级基金唯一，支持备注、标签、创建时间和最后复核时间。
- 研究记录：保存查询、筛选条件、候选、模型、数据快照和 Trace。
- 账户删除：删除或匿名化个人数据，并保留必要的系统审计信息。
- 数据导出：导出用户自己的观察列表和研究记录。

### 9.3 前端任务

1. 使用 Vue Router 区分筛选、详情、对比、观察、目标与风险、复盘和设置。
2. 使用 Pinia 或等价服务状态层统一管理：用户、数据模式、加载、错误、缓存和当前快照。
3. 所有筛选控件都绑定同一请求模型；禁止出现“页面看起来选中，但请求没有携带”的状态。
4. 观察备注调用后端保存，按观察项而不是全局 `noteDraft` 保存。
5. 风险画像页面真正调用 GET/POST；未登录用户显示只读说明。
6. 复盘页至少展示研究 Run、数据截至时间、指标版本、模型版本和后续复核项。
7. 前端不保存服务端 Key；Production 不显示 BYOK 输入框。

### 9.4 验收

- 两个测试用户互相无法读写观察列表、风险画像和研究记录。
- 刷新浏览器、重启 API、切换 API 实例后用户数据仍存在。
- 观察、备注、风险画像和研究记录均有成功/失败/重试反馈。
- 前端端到端测试覆盖登录、筛选、详情、观察、对比和研究失败状态。

## 10. Phase 5：生产部署、监控和合规

**目标：** 具备可发布、可监控、可恢复和可审计的生产基础。

### 10.1 部署拓扑

```text
CDN / HTTPS / Reverse Proxy
       |
       +--> frontend static assets
       +--> /api -> FastAPI instances
                         |
                         +--> PostgreSQL
                         +--> Redis（可选）
                         +--> Worker process
```

要求：

- API 和 Worker 使用独立进程，不能让 Render 单个 Web 进程承担周期任务。
- 生产数据库使用托管 PostgreSQL，开启自动备份和 point-in-time recovery（如供应商支持）。
- Secret 只注入后端和 Worker，不进入 Vite 构建产物。
- 前端和 API 尽量使用同源路径，减少跨域配置和 Key 泄露面。
- 部署配置固定 Python、Node 和依赖版本；requirements 使用锁定或可复现方案。

### 10.2 监控指标

至少采集：

- API 请求数、延迟、5xx、429、按路由统计。
- 数据源成功率、耗时、最近成功时间、字段缺失数、过期快照数。
- Worker 成功/失败/重试/dead-letter 数量和队列积压。
- 数据库连接池、慢查询、磁盘空间和备份状态。
- LLM 调用数、延迟、错误率、token 用量和成本估算。
- 研究 Run 完成率、候选为空比例、证据校验失败比例。

### 10.3 告警门槛示例

- 数据源连续 3 次失败。
- 关键基金快照超过新鲜度阈值。
- Worker dead-letter 非零或积压超过阈值。
- API 5xx、429 或 P95 延迟超过目标。
- LLM 成本或调用量超过日预算。
- 数据库备份失败。

### 10.4 CI/CD

Pull Request 必须执行：

```text
Python 格式/静态检查
Python 单元测试和 API 测试
数据库 migration 校验
TypeScript typecheck
前端 build
前端 E2E smoke test
依赖安全扫描
git diff --check
```

生产发布流程：

1. 合并到 release 分支。
2. 在 staging 执行数据库迁移和数据同步 smoke test。
3. 运行回归数据集和研究结果质量检查。
4. 备份数据库并记录 release、migration、policy、metric、model 版本。
5. 灰度发布 API/Worker。
6. 观察错误率、数据源状态和队列积压。
7. 通过后扩大流量；失败则回滚应用版本，数据库只执行经过验证的向前兼容迁移。

### 10.5 合规清单

- AKShare、授权供应商或官方源的访问、缓存、再分发和署名边界。
- 隐私政策、Cookie/本地存储说明、账户删除和数据导出。
- 基金研究工具与投资顾问、自动投顾、交易建议的边界审查。
- LLM 数据传输说明、第三方模型保留策略和用户提示。
- 页面免责声明必须与实际数据模式一致，不能用免责声明掩盖错误数据。

### 10.6 验收

- 数据库可从备份恢复到 staging，并通过完整 API smoke test。
- 任意一次研究结果能定位到 release、数据快照、策略、指标和模型版本。
- 关键服务异常能够告警，且有值班处理和回滚步骤。
- 生产环境依赖扫描无未接受的高危漏洞。

## 11. API 迁移清单

### 11.1 保留并升级的接口

| 接口 | 当前问题 | 改造要求 |
|---|---|---|
| `GET /health` | 只代表进程存活 | 保留；不承诺数据可用 |
| `GET /ready` | 不存在 | 新增数据库、配置、快照就绪检查 |
| `GET /api/funds` | 可能触发外部抓取 | 只读快照，支持分页、截至时间和模式 |
| `GET /api/funds/{code}` | 字段缺失原因不足 | 返回当前 profile 快照和质量摘要 |
| `GET /api/funds/{code}/history` | 按请求读取上游 | 从 NAV 快照读取，返回窗口、样本和指标版本 |
| `POST /api/funds/screen` | 缺失字段可能放行 | 返回候选、排除原因、策略和数据快照 |
| `POST /api/funds/compare` | 前端未充分使用 | 统一快照和窗口，返回指标质量 |
| `POST /api/recommendations/runs` | Run 只在内存，证据校验不足 | 认证、持久化、幂等键、状态机和限额 |
| `GET /api/watchlist/items` | 共享内存 | 认证后按 `user_id` 查询 |
| `POST /api/watchlist/items` | 匿名共享写 | 认证、幂等、基金存在性和审计 |
| `GET/POST /api/profile/risk` | GET 固定值，POST 缺失 | 用户级问卷版本化 |
| `POST /api/data/funds/refresh` | 任意人可触发 | 管理员权限、任务 ID、异步执行 |

### 11.2 推荐响应元数据

所有基金研究响应至少包含：

```json
{
  "dataMode": "REFERENCE",
  "sourceType": "AKSHARE_PUBLIC",
  "trustLevel": "LOW",
  "dataSnapshotId": "snap_20260908_001",
  "asOf": "2026-09-08",
  "qualityStatus": "ACTIVE",
  "policyVersion": "research-policy-v1",
  "metricVersion": "metric-v1"
}
```

生产模式不得返回 `AKSHARE_PUBLIC` 作为唯一主来源，也不得固定返回 `qualityStatus=REFERENCE`。

### 12.1 单元测试

## 14. 风险、回滚和停止线

### 14.1 主要风险

| 风险 | 预防 | 发生后的处理 |
|---|---|---|
| Provider 字段变化 | 列集合测试、解析器版本、原始响应保留 | 停止写入新快照，保留旧快照并告警 |
| 数据源连续失败 | 任务重试、退避、质量状态 | 降级为旧快照，超过阈值停止核心推荐 |
| 数据许可不明确 | 先完成供应商审核 | 保持 Reference，不公开再分发或切换授权源 |
| LLM 输出越界 | Schema、候选白名单、证据校验 | Run 标记失败，不回退成伪推荐 |
| 数据库迁移失败 | staging 演练、备份、向前兼容 | 停止发布，回滚应用版本并按预案恢复 |
| API 被滥用 | 认证、限流、配额和管理员隔离 | 临时关闭写接口或模型研究入口 |
| 指标口径变化 | `metric_version` 和回归集 | 新旧版本并存，禁止覆盖旧结果 |

### 14.2 不能带病上线的条件

出现以下任一情况，必须退回上一发布级别：

- 生产数据源授权或再分发边界未确认。
- 观察列表、风险画像或研究记录仍是共享内存状态。
- 未登录用户可以修改其他用户数据。
- 关键硬约束缺失字段仍被视为通过。
- 研究结果中的数值无法回查到指标快照。
- 数据源失败后页面仍把旧数据标为最新或 `ACTIVE`。
- 数据库无可验证备份，或恢复演练失败。
- CI 存在未接受的高危安全漏洞。

## 17. 最终判断标准

项目可以从“Reference Demo”升级为“小范围 Beta”，需要满足：

- 20-50 只基金拥有可追溯历史 NAV 和指标快照。
- 数据同步、过期、失败和补偿状态可见。
- 用户登录后观察、风险画像和研究 Run 持久化且互相隔离。
- 筛选结果的硬约束和缺失字段语义经过测试。
- LLM 只解释候选事实，所有数值结论都有证据引用。
- 重启、多实例和上游短时故障不会丢数据或产生伪最新状态。

项目可以从“小范围 Beta”升级为“Production”，还需要：

- 授权/官方数据源和再分发审核完成。
- 完成备份恢复、监控告警、CI/CD、压测、安全和隐私审核。
- 生产环境所有高风险问题有明确接受记录或已修复。
- 完成至少一次灰度发布和一次故障回滚演练。

在此之前，产品文案和部署配置应继续使用 `REFERENCE`，不要使用“实时”“官方”“推荐”“生产数据”等会改变用户理解的表述。
