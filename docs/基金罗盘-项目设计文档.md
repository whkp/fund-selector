# 基金罗盘：AKShare + Python AI 基金研究系统设计文档

**文档版本：v1.0**
**更新时间：2026-08-09**
**项目代号：`fund-compass`**
**适用阶段：低并发 MVP、公开演示、小规模试用**

## 1. 文档目标

本文档定义基金罗盘以 **Vue 3 + FastAPI + AKShare + PostgreSQL + Python Worker + 受控 Agent** 建设真实公开参考数据研究系统的目标方案。

系统定位为基金研究与筛选工具，不是交易系统、自动投顾或收益预测系统。产品帮助用户完成：

- 搜索基金、理解基金基本资料和数据口径；
- 按风险、期限、费用、主题和流动性筛选基金；
- 比较同类基金的历史收益和风险指标；
- 保存观察列表和研究记录；
- 通过 AI 理解自然语言目标，并基于已验证数据组织研究结论。

系统不提供：

- 基金申购、赎回、自动交易或自动调仓；
- 个股推荐、股票评分和股票交易；
- 保证收益、预测收益或确定性买卖建议；
- 将第三方网页摘要直接当作基金事实。

## 2. 技术路线结论

GitHub 上可参考的基金项目主要使用 Python：

| 项目类型 | 典型技术 | 借鉴内容 |
|---|---|---|
| Tushare + Streamlit 基金分析 | Python、Pandas、NumPy、Tushare Pro | 基于历史净值计算收益、波动率、回撤、夏普和基准对比。 |
| AKShare 基金筛选助手 | Python、AKShare、TTL 缓存 | 全量基金目录、基金排行、历史净值、ETF 行情和缓存。 |
| AKShare 批量分析器 | Python、AKShare、Pandas | 批量下载、风险计算、评分和结果导出。 |

本项目采用以下技术路线：

```text
Vue 3 + TypeScript + Vite
              |
              v
FastAPI Python 单体后端
              |
              +--> PostgreSQL：事实、历史、快照、用户和研究审计
              +--> AKShare Adapter：开发阶段主数据入口
              +--> Python Worker：同步、校验、指标和索引任务
              +--> Redis（第二阶段按需）：缓存、限流、任务锁
              +--> LLM Gateway：OpenAI-compatible 云端模型
              +--> Agent Runtime：结构化意图、只读工具、证据校验
```

### 2.1 为什么选择 Python

当前阶段没有高并发、超低延迟行情或交易接入需求，最稀缺的是基金数据处理和研究计算能力。Python 直接拥有：

- AKShare、Tushare 等基金数据接口生态；
- Pandas、NumPy、Polars 等数据处理工具；
- scipy、statsmodels 等统计分析工具；
- FastAPI + Pydantic 的接口和 Schema 能力；
- 较成熟的 Agent、结构化输出和评测生态。

迁移到 Python 的目标不是追求接口吞吐，而是降低真实数据、指标计算、批处理和 Agent 开发成本。未来如果出现高并发行情推送、交易连接或大量长连接需求，可以将独立行情服务、计算任务或网关重新拆为 Go 服务；当前不提前引入这种复杂度。

## 5. AKShare 数据入口设计

### 5.1 AKShare 的定位

AKShare 是当前开发阶段的统一数据入口，不是业务领域模型，也不是默认的生产授权证明。所有 AKShare 调用都必须封装在 `providers/akshare.py`，业务层只能依赖内部标准化接口。

```text
AKShare DataFrame
    -> Adapter 字段映射
    -> 标准化 Pydantic Record
    -> 结构和业务质量校验
    -> Raw Snapshot + Data Snapshot
    -> PostgreSQL
```

AKShare 版本、接口名称和字段映射必须锁定在 `pyproject.toml` 和 `parser_version` 中。接口字段发生变化时，适配器测试应先失败，禁止静默写入错误数据。

### 5.2 第一批使用的接口

| 领域 | AKShare 接口 | 结果 |
|---|---|---|
| 全市场基金目录 | `fund_name_em()` | 基金代码、名称、基础目录。 |
| 开放式基金排行 | `fund_open_fund_rank_em(symbol=...)` | 类型、单位净值、区间收益、部分排行字段。 |
| 开放式基金日频数据 | `fund_open_fund_daily_em()` | 公开日频排行和净值参考。 |
| 单基金历史净值 | `fund_open_fund_info_em(symbol=..., indicator=..., period=...)` | 单位净值/累计净值走势和区间数据。 |
| ETF 实时行情 | `fund_etf_spot_em()` | ETF 场内价格、涨跌幅、成交量等公开参考。 |
| ETF 日频数据 | `fund_etf_fund_daily_em()` | ETF 日频行情补充。 |
| 基金持仓 | `fund_portfolio_hold_em(symbol=..., date=...)` | 定期披露持仓，仅用于聚合暴露。 |
| 基金经理 | `fund_manager_em()` | 经理资料和任职信息参考。 |
| 基金评级 | `fund_rating_all()` | 评级参考，不直接作为推荐事实。 |
| 指数行情 | `stock_zh_index_daily_em(...)` | 基准比较和相对指标参考。 |

### 5.3 AKShare 适配器接口

```python
from datetime import date, datetime
from typing import Protocol

class FundUniverseProvider(Protocol):
    async def list_funds(self) -> list[FundBasicRecord]: ...

class FundHistoryProvider(Protocol):
    async def history(self, code: str, start: date, end: date) -> list[NAVRecord]: ...

class FundQuoteProvider(Protocol):
    async def etf_quotes(self, codes: list[str] | None = None) -> list[QuoteRecord]: ...

class DisclosureProvider(Protocol):
    async def events_since(self, since: datetime) -> list[DisclosureEvent]: ...
```

AKShare 本身多为同步调用。适配器中使用专用线程池或 Worker 进程执行，不能在 FastAPI 事件循环中直接运行长时间阻塞调用。每个调用必须有：

- 超时、重试和指数退避；
- 请求间隔和并发上限；
- 返回 DataFrame 列集合校验；
- 空结果和异常结果分类；
- 原始响应序列化与内容 hash；
- `sourceType=AKSHARE_PUBLIC`、`trustLevel=LOW/MEDIUM` 和许可范围。

### 5.4 AKShare 数据不可用时的处理

```text
首次失败：记录 acquisition_run 失败，不写入空快照
短期失败：读取最近通过质量门槛的快照，标记 DEGRADED
超过阈值：标记 STALE，禁止称为最新数据
字段冲突：标记 CONFLICT，保留所有来源，不自动选择高值
接口字段变更：适配器失败并报警，不静默解析
```

快照只追加，不原地覆盖。历史推荐始终绑定创建时的数据快照和指标版本。

### 6.2 字段质量状态

```text
PASS        通过校验，可进入核心研究
REFERENCE   公开聚合参考，可展示但默认不参与核心评分
STALE       超过新鲜度阈值
MISSING     没有值
CONFLICT    多源冲突
SUSPICIOUS  异常日期、异常涨跌或解析校验失败
INSUFFICIENT_HISTORY  历史样本不足
```

最低校验包括：基金代码和类型一致性、NAV 日期不晚于抓取时间、单位净值大于零、历史日期去重和排序、异常涨跌检测、累计净值与分红/拆分事件一致性、指标窗口样本充足性。

## 7. 指标与评分

### 7.1 真实指标计算

第一期只使用正式日频 NAV 计算：

| 指标 | 计算口径 | 样本不足行为 |
|---|---|---|
| 近 1/3/6/12 月收益 | 窗口首尾有效 NAV | 少于 2 点返回 `INSUFFICIENT_HISTORY`。 |
| 年化收益 | 按有效日期间隔年化 | 少于 90 个自然日不参与核心评分。 |
| 年化波动率 | 日收益率标准差 `* sqrt(252)` | 少于 60 个有效点不参与核心评分。 |
| 最大回撤 | NAV 与历史滚动高点的相对差 | 少于 2 点只展示，不评分。 |
| 夏普 | 年化超额收益 / 年化波动率 | 记录无风险利率和计算版本。 |
| 卡玛 | 年化收益 / 最大回撤绝对值 | 最大回撤为零时返回不可用。 |
| 同类分位 | 同类型、同窗口、同一快照横向比较 | 同类样本不足时标记不可比。 |

每条指标保存：`metric_version`、`window_code`、`input_snapshot_ids`、`business_date`、`calculated_at`、`risk_free_rate` 和 `insufficiency_reason`。

### 7.2 版本化评分

推荐评分不再读取 JSON 中的固定 `score`，而由 `research-score-v1` 计算：

```text
目标匹配              30%
风险适配              25%
长期风险调整表现      25%
费用与可得性          10%
数据质量              10%
```

权重仅为初始配置，必须通过固定评测集、人工评审和回测验证后再调整。每个候选返回：总分、分项贡献、排除原因、数据日期、样本数和质量状态。数据缺失不得默认给高分。

### 7.3 推荐流程

> **当前实现映射（2026-09-10）**：上述流程已实现到“硬过滤 -> 候选读取 -> 可选本地 Markdown 知识检索 -> 单次 LLM 结构化输出 -> Schema/候选代码校验”的 MVP。当前模型生成的 `score` 仍是临时研究展示分，确定性 `research-score-v1`、指标快照读取、证据级数值绑定和 Run 数据库持久化尚未完成；因此本节描述的是目标生产流程，不能将当前 Reference 页面理解为生产级推荐引擎。

```text
用户确认的风险画像
    -> 解析自然语言为 ResearchRequest
    -> 硬过滤：状态、风险、费用、流动性、数据质量、样本长度
    -> AKShare 标准化数据上的候选召回
    -> 真实指标、候选事实和知识库片段
    -> LLM 在受限候选池内生成排序、解释、追问和风险提示
    -> Schema、证据引用和免责声明校验
    -> 持久化 RecommendationRun / Trace
```

LLM 只能在服务端已筛出的真实候选池内排序和生成研究表达；不得创建基金事实、修改硬约束、编造数字或生成交易指令。模型输出必须通过 Schema、候选代码和数据来源校验；模型不可用时返回错误，不回退为规则推荐。

### 7.4 仓位复核与再平衡提醒

系统可以在用户选择并持有基金后提供仓位复核能力，但产品名称和输出不得使用确定性的“买入”“加仓”“卖出”指令。该能力定位为：基于用户确认的目标配置、真实数据快照和版本化规则，提示用户何时需要复核是否继续按计划投入、降低仓位或暂停新增。

对外输出枚举为：

```text
CONTINUE_PLAN       当前状态满足原计划，继续观察或按计划定投
REVIEW_INCREASE     当前仓位低于目标区间，建议复核是否按计划补足
REVIEW_REDUCE       当前仓位高于目标区间或风险发生变化，建议复核是否降低
PAUSE_NEW_MONEY     暂停新增投入，等待数据、状态或风险问题解决
INSUFFICIENT_DATA   数据或历史样本不足，暂不产生仓位信号
```

该输出是研究提醒，不构成交易指令、收益承诺或个性化投资建议。用户自行决定是否操作，系统不接入申购、赎回、自动调仓或券商/代销交易接口。

#### 7.4.1 基本规则

第一版以目标仓位和风险预算为主，不使用“预测最低点/最高点”或短期价格追涨杀跌规则：

```text
当前仓位 < 目标权重下限
且基金开放申购
且风险/数据质量/样本长度均通过
-> REVIEW_INCREASE

当前仓位 > 目标权重上限
-> REVIEW_REDUCE

基金暂停申购、关键字段过期、风险等级超限、最大回撤/波动超过风险预算
-> PAUSE_NEW_MONEY

其余情况
-> CONTINUE_PLAN
```

示例：目标仓位 20%，允许偏离为 +/-5%。当前仓位低于 15% 时，只能产生“建议复核是否按计划补足”；当前仓位高于 25% 时，产生“建议复核是否降低至目标区间”。规则必须附带数据日期、阈值、触发原因和版本号。

普通开放式基金仅基于正式日频 NAV 在收盘后、每周或每月复核。ETF/LOF 可额外参考场内行情，但 `marketPrice`、`officialNav` 和 `iopv` 必须保持独立字段，场内价格不替代正式净值。

#### 7.4.2 所需用户和持仓数据

| 数据 | 作用 | 当前要求 |
|---|---|---|
| 用户风险画像 | 风险等级、回撤与波动边界 | 用户主动填写并确认，不能由模型猜测。 |
| 实际持仓 | 份额、平均成本、当前估值、最后估值时间 | 用户录入或后续受控导入；不接交易账户。 |
| 目标配置 | 单基金/基金类型/主题目标权重、上下限 | 用户明确配置，支持版本化。 |
| 定投计划 | 周期、计划金额、执行日、暂停条件 | 只产生复核提醒，不自动执行。 |
| 真实指标快照 | NAV、收益、波动、回撤、样本长度和新鲜度 | 必须来自数据库快照，不能使用 Mock。 |
| 产品与事件状态 | 申赎状态、经理变更、公告、费率、清盘/转型 | 触发暂停新增或风险复核。 |

新增的数据表：

| 表 | 关键字段 | 用途 |
|---|---|---|
| `portfolio_accounts` | `id, user_id, name, base_currency` | 用户的研究账户，不连接交易账户。 |
| `portfolio_positions` | `account_id, fund_id, shares, average_cost, valued_at` | 当前持仓快照。 |
| `position_transactions` | `position_id, occurred_at, direction, shares, price, source` | 用户登记的历史操作，用于成本计算和审计。 |
| `allocation_targets` | `user_id, fund_id/type/theme, target_weight, lower_band, upper_band` | 目标仓位与容忍区间。 |
| `rebalance_policies` | `user_id, review_frequency, max_drawdown, max_volatility, cooldown_days` | 用户确认的复核规则版本。 |
| `position_review_runs` | `user_id, portfolio_snapshot_id, policy_version, data_snapshot_id` | 每次复核运行。 |
| `position_review_signals` | `run_id, signal_type, evidence_json, status, triggered_at` | 可解释的复核信号和证据。 |

#### 7.4.3 前端展示

基金详情页和持仓页增加“仓位复核”区域，至少显示：

```text
当前状态
触发时间
使用的数据截至时间
当前仓位 / 目标区间
信号依据
风险或数据提示
规则和指标版本
免责声明
```

当数据为 `REFERENCE`、`STALE`、`MISSING` 或 `INSUFFICIENT_HISTORY` 时，前端不得渲染“建议补足”或“建议降低”动作文案，只能显示数据不足、暂停新增或等待复核。

#### 7.4.4 Agent 边界

仓位信号由确定性规则引擎计算，Agent 只允许：解释信号依据、比较风险变化、生成复核清单和提出待确认问题。Agent 不得基于短期涨跌、新闻摘要或模型直觉自行创建加仓、卖出或调仓信号。

## 8. Agent 设计

### 8.1 工具注册

Agent 只能调用显式、只读、强类型工具：

```text
search_funds
get_fund_profile
get_fund_nav_history
get_fund_metrics
compare_funds
check_data_quality
analyze_watchlist_overlap
```

工具输入输出用 Pydantic Schema 校验，工具内部只能读取服务层和数据库，不能让模型拼接 SQL、直接访问 AKShare 或任意 URL。

### 8.2 Agent 状态

```text
RECEIVED
-> INTERPRETED
-> RETRIEVING
-> FILTERED
-> SCORED
-> EXPLAINING
-> VALIDATED
-> COMPLETED / DEGRADED / FAILED
```

每个 Run 保存：用户目标、结构化意图、工具参数和结果摘要、数据快照、指标版本、模型版本、Prompt 版本、输出校验结果、降级原因和 Trace。

### 8.3 LLM 配置安全

- Demo/生产关闭公网 `/api/ai/configure` 和 `/api/ai/reset`。
- 模型、Base URL、Key 由环境变量或 Secret Manager 注入后端。
- 若以后支持用户自带 Key，必须绑定用户、加密或会话级保存、host allowlist、调用限额和成本配额。
- 日志、错误、Trace 和前端状态不得出现 API Key。
- AI 失败时保留事实查询可用，但研究接口返回可解释的失败状态，不产生规则式替代推荐。
- 短期公网 MVP 支持会话级 BYOK：Key 仅随单次研究请求发送并在请求后释放，不写入用户记录或浏览器持久化存储；正式版再引入用户账户级加密连接。

## 10. 公开展示与部署

### 10.1 Reference 阶段

- 页面顶部显示 `REFERENCE`，明确基金数量、来源、时间和信任等级。
- API 或 AKShare 不可用时显示错误或空状态，禁止以本地示例数据替代真实数据。
- 禁止网页输入云端 API Key；AI 使用服务端配置。
- 写接口关闭或绑定固定演示会话。
- 使用 `npm run build` 后的静态资源，通过 Caddy/Nginx 同源代理 `/api`。

### 10.2 生产基础设施

```text
Browser -> HTTPS/CDN -> Caddy/Nginx -> FastAPI
                                  -> PostgreSQL
                                  -> Redis（可选）
                                  -> Python Worker
                                  -> Secret Manager
```

FastAPI 需要配置请求超时、请求体限制、panic/异常处理、精确 CORS、CSRF 或安全会话、速率限制、结构化脱敏日志、`/health/live`、`/health/ready` 和优雅关闭。

禁止直接把 Vite dev server、AKShare 接口或内部管理接口暴露到公网。

## 11. 测试和质量门禁

### 11.1 测试层次

- Provider contract tests：模拟 AKShare DataFrame，验证列名、类型和空结果。
- Normalizer tests：验证代码、日期、净值和来源字段映射。
- Metric tests：用固定 NAV 序列验证收益、波动、回撤、夏普和边界情况。
- Repository tests：迁移、快照追加、幂等和历史查询。
- API tests：兼容现有前端协议、错误码、认证和限流。
- Agent tests：Schema、工具白名单、硬约束、证据覆盖和模型降级。
- Regression set：固定自然语言目标和期望过滤结果，防止模型/评分变更破坏行为。

### 11.2 质量门禁

- 过期或缺失关键字段不能进入核心推荐。
- 低信任公开参考数据必须展示来源和边界。
- 所有解释中的数值必须能回查到指标快照。
- 同一快照、策略和模型版本可以重放同一 Run。
- AKShare 字段变化时适配器测试失败并报警，不静默写错数据。
- API、Worker、前端构建和 migration 在 CI 中全部通过。

## 12. 分阶段迁移计划

### Phase 0：Python 后端兼容骨架（1-2 周）

- 创建 `backend/`、FastAPI、Pydantic Schema 和 API 路由。
- 实现与当前前端 API 契约相同的路径和 JSON 字段。
- 先使用空 Repository，确保现有 Vue 页面只能在 AKShare 成功返回后显示基金数据。
- 增加 `REFERENCE`、`PRODUCTION` 配置模式。
- 关闭生产网页 AI 配置接口。

**验收：** Vue 页面不改交互即可通过 FastAPI 完成健康检查、基金列表、筛选、对比和推荐请求。

### Phase 1：AKShare 基金数据闭环（2-4 周）

- 实现 `fund_name_em` 全市场目录同步。
- 实现 `fund_open_fund_rank_em` 类型排行和基础筛选。
- 实现 `fund_open_fund_info_em` 单基金历史 NAV 同步。
- 实现 `fund_etf_spot_em` ETF 场内行情参考。
- 保存原始响应、字段映射版本、标准化快照和质量状态。
- 首批选择 20-50 只基金，完成历史 NAV 回补。

**验收：** 基金候选不再固定为 5 只；每条 NAV 有来源、抓取时间、业务日期和快照 ID。

### Phase 2：指标和动态评分（2-4 周）

- Python Worker 计算 1/3/6/12 月收益、年化收益、年化波动、最大回撤、夏普和卡玛。
- 指标保存 `metricVersion`、窗口、输入快照和样本不足原因。
- 用 `research-score-v1` 替换 `mock_metric_v1` 和 JSON 固定评分。
- 对关键指标增加 Pandas 对账脚本和回归测试。

**验收：** 基金详情曲线和指标来自历史 NAV，不再使用固定 `chart` 和固定收益字段。

### Phase 3：持久化、用户和 Agent（3-5 周）

- 引入 PostgreSQL、Alembic、SQLAlchemy Repository。
- 持久化基金事实、NAV、指标、用户风险画像、观察列表和 Recommendation Trace。
- 增加登录和 user_id 隔离。
- 增加用户持仓、目标仓位、定投计划和版本化仓位复核规则；只输出“继续计划/建议复核/暂停新增”等研究提醒。
- 注册只读 Agent 工具，加入 Pydantic Schema、Guardrail、证据绑定和重放能力。
- AI 只解析目标和组织解释，不决定事实和硬约束。

**验收：** 重启不丢数据，用户之间互不可见，任一推荐和仓位复核信号均可按数据快照、策略版本和用户配置版本重放。

### Phase 4：公开服务生产化（持续迭代）

- 完成 AKShare 使用边界和生产数据授权审核；必要时增加授权供应商适配器。
- 引入 PostgreSQL Outbox、Worker 锁、重试、补偿和数据异常队列。
- 按需引入 Redis、pgvector 或 OpenSearch，而不是预先拆分。
- 增加监控、告警、备份、恢复演练、CI/CD、压测和安全审计。
- 完成隐私政策、数据来源说明、免责声明和公开服务审核。

## 14. 最终结论

当前阶段可以迁移到 Python，而且推荐迁移。正确的迁移不是把 Go 代码逐行翻译成 Python，也不是让页面每次打开时直接抓 AKShare，而是：

```text
Vue 前端保持不变
-> FastAPI 兼容现有 API
-> AKShare 作为开发阶段数据入口
-> PostgreSQL 保存原始/标准化/指标快照
-> Python Worker 负责批量同步和计算
-> 确定性筛选与评分先于 Agent
-> Agent 只做结构化理解、只读工具编排和解释
```

第一步优先实现 Python 兼容 API 和 AKShare 基金目录/NAV Adapter；第二步实现真实历史指标；第三步再迁移推荐和 Agent。这样可以保留当前前端成果，同时让项目真正进入“真实基金数据 + Python 研究生态”的开发路径。

AKShare 适合作为开发和研究阶段的数据入口，但在系统正式公开展示或商业化前，仍必须单独完成数据授权、批量缓存、再分发和来源署名审核。
